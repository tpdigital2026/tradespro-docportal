# Owner App (login, shell, customers, quote flow, download) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A mobile-first web app where an invited business owner logs in with an emailed code, picks or adds a customer, fills a short quote form with live money totals, previews and finalises a PDF, downloads it, and copies a covering email. AI wording is a later plan; this plan ships a deterministic "tidy" seam so the AI can be dropped in without touching the screens.

**Architecture:** Next.js App Router. Auth through Supabase Auth email codes via server routes that wrap `verifyWithGuard` / `requestCodeWithGuard`. Reads and writes the owner may do go through supabase-js using the owner's session (RLS applies). Server-only writes (finalise, bank accounts, customer deletion) use the service role after checks. PDF rendering reuses `src/templates/*` and `src/pdf/*` through a `renderPdf()` seam. All screens are server components plus small client islands. A dev-only demo mode (`DEMO_MODE=1`, refused when `NODE_ENV === 'production'` or when `VERCEL` is set) uses an in-memory fake session and dummy data so every screen can be viewed without keys.

**Tech Stack:** Next.js 16, React 19, TypeScript, zod, `@supabase/supabase-js`, `@supabase/ssr`, Vitest, existing money/html/templates/pdf modules.

**Spec:** `docs/superpowers/specs/2026-10-14-docportal-design.md` (Owner flow, Auth, Quote number is the job key, Decisions update 2026-10-14). Plan 2's README "Login route requirements" and "Server rules" sections are binding on every server route here.

## Global Constraints

- Mobile first: design at 390px, then 768 and 1280. No horizontal overflow at any width. Tap targets at least 44px. Respect `prefers-reduced-motion`.
- Owner copy rules: no em dashes anywhere in UI text or docs; never the word "actually"; UK English.
- Truth rules: nothing invented. Money only from `src/lib/money.ts` (integer pence). No sample figures presented as real; demo data is clearly dummy (Mr John Smith, 123 Bromley Road, BR2 8BG, bank 00-00-00 / 00000000).
- Brand: DocPortal UI is TradesPro Digital's own tool: navy ground `#071626`, elevated `#0C2033`, brand blue `#0B9BEA`, steel `#9DB8CC`, white text, Outfit headings and Work Sans body (self-host via `@fontsource`, no network fonts). One CTA per screen. No stock imagery. Not everything is a card.
- Never print or log secrets; scripts and routes pass errors through `redactSecrets` / `redactAll`. Never read `.env.local`.
- Login responses are identical for unknown emails, locks and wrong codes. Never reveal whether an email is invited.
- Every server route: verify session, resolve tenant from `profiles` (never from client input), validate with zod, return generic errors.
- No email is ever sent by the app in Phase 1.
- `npm run test`, `npm run test:db` and `npx tsc --noEmit` pass at every commit. Commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.

### Task 2: Login, session and route protection

**Files:**
- Create: `src/lib/supabase-server.ts`, `src/lib/session.ts`, `src/app/login/page.tsx`, `src/app/login/LoginForm.tsx`, `src/app/api/auth/request-code/route.ts`, `src/app/api/auth/verify/route.ts`, `src/app/api/auth/logout/route.ts`, `src/proxy.ts` (Next 16 request proxy; check the installed Next docs for the exact name), `src/lib/client-ip.ts`
- Test: `tests/auth-routes.test.ts`, `tests/session.test.ts`

**Interfaces:**
- Consumes: `requestCodeWithGuard`, `verifyWithGuard`, `normaliseIp` from `src/security/login-guard.ts`; `connect()` from `src/db/connect.ts`.
- Produces: `getSession(): Promise<{ userId; tenantId; role; email; fullName } | null>` (server; in demo mode returns `demoSession`); `requireSession()` (redirects to `/login`); route handlers as above.

- [ ] Two-step login UI (email, then 6-digit code with `autocomplete="one-time-code"` and `inputmode="numeric"`); copy never reveals whether the email is invited ("If that email is registered, a code is on its way").
- [ ] `request-code`: zod email, trusted client IP, `requestCodeWithGuard` on a dedicated connection, then `signInWithOtp({ shouldCreateUser: false })` only when the email has an active profile; identical 200 response either way; map `LOGIN_GUARD_BUSY`/`55P03` to a generic try-again response.
- [ ] `verify`: `verifyWithGuard` wrapping `verifyOtp`; identical failure for wrong code, lock and unknown email; sets the session cookies (httpOnly, secure outside dev, sameSite lax); 15 minute lock behaviour per Plan 2.
- [ ] `getSession` resolves tenant and role from `profiles` (active only). Proxy redirects unauthenticated requests for `(app)` routes to `/login`; static assets and `/login`, `/api/auth/*` public. CSRF: state-changing routes require same-origin `Origin`.
- [ ] Tests with a stubbed Supabase client and a stub guard: identical responses, lock mapping, no email enumeration, redirect behaviour.
